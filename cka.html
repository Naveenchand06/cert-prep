Fast manifest workflow

k run web --image=nginx --dry-run=client -o yaml > pod.yaml
vi pod.yaml
k apply -f pod.yaml
k get pod web -o yaml

Generate a valid starting point. Add fields that kubectl doesn't expose as flags (probes, securityContext, volumes, affinity) in YAML.

Remember the short flags

-n namespace · -A all namespaces · -o wide node/IP view · -o yaml manifest · -f file · -l label selector · --tail log lines · -w watch
Verify: After every change, query the object or test connectivity. A green command exit code does not prove the requested outcome.

Inspect processes on the task node

Follow the task's host instruction (for example, ssh controlplane) and elevate if needed. Repeat on each node named by the task.

ssh <designated-node>
sudo -i

# kubelet is a systemd service on every node
systemctl status kubelet --no-pager
systemctl cat kubelet
journalctl -u kubelet -n 100 --no-pager

# CRI containers, including control-plane static Pods
crictl ps -a
crictl pods
crictl ps -a --name kube-apiserver
crictl logs <container-id>

# Host process view; control-plane components run as containers
ps -ef | grep -E '[k]ubelet|[k]ube-apiserver|[k]ube-scheduler|[k]ube-controller-manager|[e]tcd'

# API view when the API server is healthy
k get pods -n kube-system -o wide
k describe pod kube-apiserver-<node> -n kube-system

# Check kubelet's actual static manifest path
grep -n 'staticPodPath' /var/lib/kubelet/config.yaml

If crictl cannot find the runtime socket, inspect systemctl cat kubelet and /var/lib/kubelet/kubeadm-flags.env for its configured CRI endpoint. Workers normally run kubelet and workload containers; control-plane components are usually absent.

Back up stacked etcd

Run on the control-plane host that runs local etcd. Confirm endpoint and certificate paths in etcd.yaml; external etcd uses its own endpoint and credentials.

# Keep the snapshot outside etcd's live data directory
sudo install -d -m 700 /opt/etcd-backup

sudo ETCDCTL_API=3 etcdctl \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /opt/etcd-backup/snapshot.db

# Preferred verification (etcdutl version should match etcd)
sudo etcdutl --write-out=table snapshot status /opt/etcd-backup/snapshot.db
# If etcdutl is unavailable in the lab, this older etcdctl form may exist:
sudo ETCDCTL_API=3 etcdctl --write-out=table snapshot status /opt/etcd-backup/snapshot.db
sudo ls -lh /opt/etcd-backup/snapshot.db
  • 1Check the etcd container flags if endpoint or certificate names differ.
  • 2Use an etcdutl version compatible with the etcd major/minor for status and restore.
  • 3Snapshots contain cluster secrets and state; protect them and keep them off the live data path.
Restore is separate and disruptive. Do not restore during a backup task; restore changes the data directory and static Pod configuration.

What the exam confirms

The published CKA competencies explicitly include creating and managing clusters with kubeadm. Linux Foundation instructions say tasks identify a designated SSH host. Public guidance does not promise every prebuilt exam cluster is exclusively kubeadm-created, so treat these as kubeadm defaults and inspect the actual host configuration.
